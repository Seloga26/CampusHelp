# HU-11 — Gestionar categorías

## Identificación

- **Tipo de caso relacionado:** Incidente y Solicitud de servicio
- **Área / Categoría:** Todas
- **Prioridad:** P2
- **Story Points:** 3
- **Dependencias:** ninguna. HU-01 ya ofrece solo categorías activas y rechaza las inactivas (CP-11).
- **Responsable:** Miguel (@miguelfsociety, asignado en Issue #11)

## Historia

Como **administrador**, quiero **gestionar categorías de soporte**, para **mantener actualizada la clasificación de los casos**.

## Reglas de negocio

1. Solo un usuario activo con rol **Administrador** crea, edita, desactiva o reactiva categorías.
2. Toda categoría pertenece a un **área activa** existente (Taller, sección 7). Las áreas son las 5 del Taller y no se gestionan en esta historia.
3. **Nombre** obligatorio, de 3 a 100 caracteres después de quitar espacios; **descripción** opcional, de hasta 255.
4. No puede haber dos categorías con el mismo nombre en la misma área, sin distinguir mayúsculas ni tildes (lo garantiza `uq_categoria_area_nombre` con la intercalación `utf8mb4_unicode_ci`). Repetido → 409.
5. **No se borran categorías:** se desactivan. Una categoría inactiva deja de aparecer al registrar casos, pero los casos que ya la tienen la conservan y la siguen mostrando.
6. Una categoría inactiva se puede reactivar.
7. La lista de gestión muestra todas las categorías (activas e inactivas) agrupadas por área, con la cantidad de casos que tiene cada una.

## Criterios de aceptación

**Escenario 1 — Crear (CP-36)**
- Given el área Red y conectividad
- When Fabio (Administrador) crea la categoría "VPN institucional"
- Then queda activa y aparece al registrar un caso de esa área

**Escenario 2 — Nombre repetido (CP-37)**
- Given la categoría "Wi-Fi" en Red y conectividad
- When se intenta crear "wi-fi" en la misma área
- Then el sistema responde 409 y no se crea nada

**Escenario 3 — Desactivar (CP-38)**
- Given la categoría "Impresora" con casos registrados
- When Fabio la desactiva
- Then ya no aparece en el formulario de registro, pero los casos existentes siguen mostrando "Impresora"

**Escenario 4 — Usuario sin permiso (CP-39)**
- Given un usuario con rol Agente
- When intenta crear o editar una categoría
- Then el sistema responde 403 y no cambia nada

## Contrato de API

```json
// GET /api/categorias                       (sin cambios: activas, para el registro)
// GET /api/categorias/areas                 → áreas activas, incluidas las que no tienen categorías
// GET /api/categorias/gestion?usuario_id=6  → todas, con "activa" y "casos"
// POST /api/categorias
{ "area_id": 3, "nombre": "VPN institucional", "descripcion": "Acceso remoto", "usuario_id": 6 }
// 201 → categoría creada
// PATCH /api/categorias/:id
{ "nombre": "VPN", "descripcion": "…", "activa": false, "usuario_id": 6 }   // campos opcionales
// 200 → categoría actualizada
// 400 datos inválidos o área inexistente/inactiva | 403 no es Administrador | 404 categoría no existe | 409 nombre repetido en el área
```

## Implementación verificada (2026-10-12)

Rama exclusiva `feature/HU-11-gestionar-categorias`, creada desde `main`
(`a9adf75`) después de integrar HU-06. Se implementa la gestión con permisos
de administrador activo, validación de datos, edición parcial y desactivación
sin borrar categorías ni modificar casos. Los duplicados concurrentes se
traducen a 409 mediante el índice real de MySQL.

La página agrupa el catálogo por área, muestra estado y cantidad de casos,
evita doble envío y conserva el formulario ante errores. El catálogo de áreas
activas se consulta por separado para permitir crear la primera categoría de
un área vacía. Los menús compartidos solo reciben el enlace a Categorías.

## Decisiones de refinamiento

- **¿Por qué no borrar?** Los casos guardan `categoria_id`; borrar rompería el historial de clasificación. Desactivar cumple la necesidad sin perder datos.
- **¿Se gestionan áreas?** No: el Taller fija las 5 áreas. Agregar áreas sería un PBI nuevo.
- **¿Se registra en el historial?** No: el historial es por caso, y estas acciones no cambian ningún caso.
