# HU-07 — Aprobar o devolver una solución

## Identificación

- **Tipo de caso relacionado:** Incidente y Solicitud de servicio
- **Área / Categoría:** Todas
- **Prioridad:** P1
- **Story Points:** 5
- **Dependencias:** HU-06 (el caso debe tener una solución registrada) y HU-05 (el caso llega a En validación).
- **Responsable:** Keyla (propuesto)

## Historia

Como **validador**, quiero **aprobar o devolver una solución**, para **controlar la calidad**.

## Reglas de negocio

1. Solo un usuario activo con rol **Validador** puede aprobar o devolver.
2. El caso debe estar **En validación**.
3. **Aprobar:** el caso pasa a **Cerrada** y se guarda `fecha_cierre`. Antes se verifica que tenga al menos una atención registrada (Taller: no cerrar sin solución).
4. **Devolver:** el caso vuelve a **En atención** con el mismo agente asignado. El **motivo** es obligatorio, de 10 a 100 caracteres, y queda en el historial.
5. Cada decisión se registra en `historial`: "Solución aprobada" (En validación → Cerrada) o "Solución devuelta: \<motivo\>" (En validación → En atención). Caso e historial van en una transacción.
6. Un caso Cerrada ya no cambia (regla existente en `domain/estados.js`).

## Criterios de aceptación

**Escenario 1 — Aprobar (CP-09)**
- Given un caso En validación con una atención registrada
- When Elena (Validadora) aprueba la solución
- Then el caso queda Cerrada con fecha de cierre y el historial tiene "Solución aprobada"

**Escenario 2 — Devolver (CP-08)**
- Given un caso En validación
- When Elena lo devuelve con el motivo "La impresora sigue sin imprimir"
- Then el caso vuelve a En atención y el historial tiene el evento con el motivo

**Escenario 3 — Usuario sin permiso (CP-23)**
- Given un usuario con rol Agente
- When intenta aprobar una solución
- Then el sistema responde 403 y no cambia nada

**Escenario 4 — Estado incorrecto (CP-24)**
- Given un caso En atención
- When Elena intenta aprobarlo
- Then el sistema responde 409

**Escenario 5 — Devolver sin motivo (CP-25)**
- Given un caso En validación
- When Elena lo devuelve sin motivo o con menos de 10 caracteres
- Then el sistema responde 400 y el caso sigue En validación

## Contrato de API

```json
// POST /api/casos/:id/validacion
{ "decision": "aprobar", "usuario_id": 5 }
{ "decision": "devolver", "motivo": "La impresora sigue sin imprimir", "usuario_id": 5 }
// 200 → caso actualizado
// 400 decisión o motivo inválidos | 403 no es Validador | 404 caso no existe | 409 no está En validación o no tiene solución

// GET /api/casos/:id/atenciones  (para mostrar la solución al validador)
// 200 → [{ "id", "diagnostico", "solucion", "fecha", "agente" }] (la más reciente primero) | 404
```

## Decisiones de refinamiento

- **¿Dónde se guarda el motivo de la devolución?** En el texto del evento del historial (columna `evento`, 120 caracteres). Por eso el motivo se limita a 100 caracteres y no hace falta cambiar el esquema.
- **¿Cualquier validador o uno asignado?** Cualquier validador activo: el Taller no define asignación de validadores.
- **¿Al devolver se cambia el agente?** No: vuelve al mismo agente, que registra una nueva atención (HU-06).
