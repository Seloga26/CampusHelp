## Historia

Como **agente**, quiero **asignarme un caso**, para **asumir su atención**.

## Reglas de negocio

1. Solo un usuario activo con rol Agente puede asignarse un caso. El agente es quien está en "Actuar como" (`usuario_id`).
2. Se puede asignar un caso en cualquier estado excepto Cerrada.
3. Si el caso ya tiene otro agente asignado, se rechaza: la reasignación no está en el alcance del MVP.
4. Si el agente ya es el asignado, se rechaza con un mensaje claro (no se duplica historial).
5. Al asignar se guardan `agente_id` y `fecha_asignacion`, y se registra en `historial` el evento "Caso asignado" (sin cambio de estado). Ambas escrituras van en una transacción.
6. Asignar **no** cambia el estado; el agente lo avanza con HU-05.
7. **Cambio en HU-05 (regla del Taller, sección 7):** desde este sprint, solo el agente **asignado** puede cambiar el estado de un caso. Un caso sin asignar no puede salir de Pendiente.

## Criterios de aceptación

**Escenario 1 — Asignación válida (CP-06)**
- Given un caso Pendiente sin agente
- When Carla (Agente) se lo asigna
- Then el caso queda con agente Carla y fecha de asignación, y el historial tiene el evento "Caso asignado"

**Escenario 2 — Caso ya asignado a otro (CP-17)**
- Given un caso asignado a Carla
- When Diego (Agente) intenta asignárselo
- Then el sistema responde 409 y el caso sigue asignado a Carla

**Escenario 3 — Usuario sin permiso (CP-18)**
- Given un usuario con rol Solicitante
- When intenta asignarse un caso
- Then el sistema responde 403 y no cambia nada

**Escenario 4 — Solo el asignado cambia el estado (CP-19)**
- Given un caso asignado a Carla
- When Diego intenta pasarlo a En análisis
- Then el sistema responde 403 y el estado no cambia

## Contrato de API

```json
// PATCH /api/casos/:id/asignar
{ "usuario_id": 3 }
// 200 → caso actualizado (con "agente": "Carla Agente")
// 400 datos inválidos | 403 no es Agente | 404 caso no existe | 409 cerrado o ya asignado
```

## Implementación

- **Doble asignación:** el caso se lee con bloqueo de fila (`FOR UPDATE`) y además el `UPDATE` solo actúa si `agente_id IS NULL`. Si otro agente lo tomó, se responde 409 y no se escribe historial.
- **Orden de las comprobaciones en HU-05:** un caso Cerrado sigue respondiendo 409; después se exige el agente asignado (403) y luego la transición (409). Así, un caso sin agente responde 403 aunque la transición pedida tampoco sea válida.
- **Efecto en las pruebas de HU-05 y HU-06:** sus casos de prueba ahora parten asignados al agente que los avanza. La prueba de navegador de la bandeja ya no prepara la asignación con SQL: usa el botón Asignarme.

## Decisiones de refinamiento

- **¿Un agente asigna a otro?** No: la historia dice "asignarme". La asignación por un coordinador quedaría como PBI nuevo si el cliente lo pide (evento E5).
- **¿Asignar mueve el caso a En análisis?** No. Así cada acción deja su propio evento en el historial y HU-05 sigue siendo la única que cambia estados.
- **¿Qué pasa con casos que ya están en análisis sin agente?** Con la regla 7 no podrán avanzar hasta que alguien se los asigne. Es lo esperado.
