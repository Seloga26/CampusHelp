# HU-09 — Filtrar casos

## Identificación

- **Tipo de caso relacionado:** Incidente y Solicitud de servicio
- **Área / Categoría:** Todas
- **Prioridad:** P2
- **Story Points:** 3
- **Dependencias:** HU-02 y HU-03 (`GET /api/casos` y `casosRepository.listar`, Sprint 1).
- **Responsable:** Keyla (propuesto)

## Historia

Como **administrador**, quiero **filtrar casos**, para **encontrarlos rápidamente**.

## Reglas de negocio

1. Filtros del Taller (sección 4): **estado, tipo, área, categoría y prioridad**. Todos son opcionales y se combinan con Y (deben cumplirse todos).
2. Los filtros se aplican sobre **todos los casos**, incluidos los cerrados, en orden del más reciente al más antiguo.
3. Cada filtro solo acepta valores del catálogo: estados de `domain/estados.js`, tipos y prioridades de `domain/catalogos.js`, y `area_id` / `categoria_id` como enteros positivos. Un valor fuera del catálogo responde 400 con un mensaje claro.
4. Un filtro repetido en la URL (`?prioridad=P1&prioridad=P2`) se rechaza con 400: el MVP filtra por un solo valor por campo.
5. Si nada coincide, la respuesta es una lista vacía (200), no un error.
6. Los filtros son compatibles con `usuario_id` (HU-02) y `vista=bandeja` (HU-03), que siguen funcionando igual.
7. El SQL se arma con parámetros (`?`); los valores del usuario nunca se concatenan.

## Criterios de aceptación

**Escenario 1 — Filtro combinado (CP-10)**
- Given casos de varios tipos, áreas y prioridades
- When el administrador filtra por tipo Incidente, área Red y conectividad y prioridad P1
- Then solo aparecen los casos que cumplen las tres condiciones

**Escenario 2 — Estado y categoría (CP-29)**
- Given casos Pendientes y Cerrados en la categoría Wi-Fi y en otras categorías
- When filtra por estado Cerrada y categoría Wi-Fi
- Then solo aparecen los casos cerrados de Wi-Fi

**Escenario 3 — Valor inválido (CP-30)**
- Given la API de casos
- When se pide `?prioridad=P9` o `?estado=Abierto`
- Then responde 400 con el valor permitido en el mensaje

**Escenario 4 — Sin coincidencias (CP-31)**
- Given ningún caso P3 en Plataformas académicas
- When se filtra por esa combinación
- Then la pantalla muestra "No hay casos con esos filtros" y la API responde una lista vacía

## Contrato de API

```json
// GET /api/casos?estado=Pendiente&tipo=Incidente&area_id=3&categoria_id=8&prioridad=P1
// 200 → misma forma que hoy (id, tipo, titulo, prioridad, estado, area, categoria, solicitante, agente, fecha_creacion)
// 400 → { "error": "prioridad inválida. Valores permitidos: P1, P2, P3" }
```

## Decisiones de refinamiento

- **¿En qué pantalla?** En una página nueva, `casos.html`, para el administrador. La bandeja del agente no cambia.
- **¿Hace falta permiso?** No se agrega: `GET /api/casos` ya es de solo lectura y no hay autenticación real en el MVP.
- **¿Búsqueda por texto?** No está en el Taller; quedaría como PBI nuevo si el cliente la pide (evento E5).
