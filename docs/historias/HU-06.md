# HU-06 — Registrar diagnóstico y solución

## Identificación

- **Tipo de caso relacionado:** Incidente y Solicitud de servicio
- **Área / Categoría:** Todas
- **Prioridad:** P1
- **Story Points:** 5
- **Dependencias:** HU-04 (agente asignado, Sprint 2) y HU-05 (el caso debe estar En atención, Sprint 1).
- **Responsable:** Miguel (@miguelfsociety, asignado en Issue #6)

## Historia

Como **agente**, quiero **registrar diagnóstico y solución**, para **documentar la atención**.

## Reglas de negocio

1. Solo el **agente asignado** al caso puede registrar la atención (Taller, sección 7).
2. El caso debe estar **En atención**.
3. Diagnóstico y solución son obligatorios, con un mínimo de 10 caracteres cada uno.
4. Cada registro crea una fila nueva en `atencion` (con fecha y agente). Un caso puede tener varias atenciones: por ejemplo, si el validador lo devuelve (HU-07), el agente registra una nueva.
5. Registrar la atención **no** cambia el estado. El agente lo envía a validación con HU-05.
6. Se registra en `historial` el evento "Atención registrada" (sin cambio de estado). Atención e historial van en una transacción.
7. **Cambio en HU-05 (Taller: "no cerrar sin solución"):** un caso no puede pasar de En atención a En validación si no tiene al menos una atención registrada. Así el validador nunca recibe un caso sin solución.

## Criterios de aceptación

**Escenario 1 — Registro válido (CP-07)**
- Given un caso En atención asignado a Carla
- When Carla registra diagnóstico y solución válidos
- Then la atención queda guardada con fecha y agente, y el historial tiene "Atención registrada"

**Escenario 2 — Agente no asignado (CP-20)**
- Given un caso asignado a Carla
- When Diego intenta registrar la atención
- Then el sistema responde 403 y no se guarda nada

**Escenario 3 — Estado incorrecto (CP-21)**
- Given un caso En análisis
- When el agente asignado intenta registrar la atención
- Then el sistema responde 409

**Escenario 4 — Validación sin solución (CP-22)**
- Given un caso En atención sin atenciones registradas
- When el agente intenta pasarlo a En validación
- Then el sistema responde 409 y el estado no cambia

## Contrato de API

```json
// POST /api/casos/:id/atencion
{ "diagnostico": "El AP del bloque B estaba apagado", "solucion": "Se reinició el AP y se verificó la conexión", "usuario_id": 3 }
// 201 → { "id", "caso_id", "diagnostico", "solucion", "fecha", "agente_id" }
// 400 datos inválidos | 403 no es el agente asignado | 404 caso no existe | 409 el caso no está En atención
```

## Decisiones de refinamiento

- **¿Diagnóstico y solución por separado?** No: se registran juntos en un solo paso. Separarlos agregaría estados intermedios sin valor para el MVP.
- **¿Se puede editar una atención?** No. Si la solución cambia, se registra una nueva; el historial queda completo.
- **"Cuando el tipo de atención lo requiera":** para el MVP, todo caso (Incidente o Solicitud) requiere solución antes de validarse.
