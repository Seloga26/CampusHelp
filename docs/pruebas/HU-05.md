# HU-05 — Guía de implementación, pruebas e integración

Issue: [#5](https://github.com/Seloga26/CampusHelp/issues/5). Responsable: Miguel
(@miguelfsociety). Rama de integración: `feature/HU-05-integrar-bandeja`.
La implementación original de backend está en `feature/HU-05-cambiar-estado`
y se integró en `main` junto con HU-06 mediante PR #27.

**Uso desde la rama de HU-06:** `feature/HU-06-registrar-atencion` conserva este
backend y añade la restricción del Sprint 2: antes de pasar a En validación,
registrar diagnóstico y solución desde `/atender.html?id=<caso>` con el agente
asignado. Sin atención, la API devuelve 409. La guía y las cifras del 5/6 de
octubre describen la versión original de HU-05; la evidencia de la versión
ampliada está en [HU-06.md](HU-06.md).

## Implementación

- `src/services/casos/cambiarEstado.js`: validación de IDs, agente y transición;
  coordina caso + historial mediante `enTransaccion`. Errores de dominio 400,
  403, 404 y 409. Recibe las dependencias del contenedor.
- `src/repositories/casosRepository.js`: búsqueda con `SELECT … FOR UPDATE` para
  validar cambios concurrentes; actualización y fecha inicial con `COALESCE`;
  consulta final con área, categoría, solicitante y agente.
- `src/repositories/historialRepository.js`: repositorio de HU-01 reutilizado para
  registrar el evento con la misma conexión de la transacción.
- `src/routes/casosRoutes.js`: la ruta PATCH de HU-05 ya está conectada al servicio
  desde la refactorización de ADR-003 y se conserva.
- `public/js/estado-caso.js`: control para el siguiente estado, errores visibles,
  actualización tras guardar y protección frente a doble clic.
- `/cambiar-estado.html`: pantalla independiente con selector de agentes para
  trabajar mientras se integra HU-03. No consulta ni implementa la bandeja.

El cierre y la devolución desde validación siguen reservados a HU-07. En Sprint 1
se permite actuar a cualquier agente activo, según el refinamiento de la historia.

## Prueba automática con MySQL real

Con MySQL 8 disponible y las credenciales de `.env` configuradas:

```powershell
$env:CAMPUSHELP_TEST_MYSQL = '1'
node --test tests/casosEstado.mysql.test.js
Remove-Item Env:CAMPUSHELP_TEST_MYSQL
```

La cuenta necesita permisos para crear una base temporal y triggers. La prueba
crea `campushelp_hu05_test_<identificador aleatorio>`, aplica esquema y seed en esa
base y la elimina al terminar. La base de la aplicación no se altera. Incluye los
criterios de aceptación, fechas, dos cambios simultáneos y un fallo deliberado de
INSERT en historial para verificar rollback real. Se omite en `npm test` normal.

## Prueba manual de la pantalla

1. Iniciar MySQL y `npm start`. El seed contiene cuatro casos; también se puede
   registrar uno desde `/registrar.html`. No reinicializar una BD con datos del equipo.
2. Abrir `http://localhost:3000/bandeja.html`, seleccionar Carla o Diego y
   localizar un caso Pendiente.
3. Pulsar **Pasar a En análisis** y **Pasar a En atención**. Cada éxito actualiza
   la tabla. Para enviar a validación se necesita una atención de HU-06: en un
   caso ya asignado al agente seleccionado, pulsar **Registrar atención**,
   guardar diagnóstico y solución, volver a **Bandeja** y pulsar **Pasar a En
   validación**. Sin solución, la API responde 409 y el error aparece en la fila.
   Los casos sin asignar dependen del flujo pendiente de HU-04 para registrar atención.
4. Consultar la BD con el ID utilizado:

```sql
SELECT id, estado, fecha_inicio_atencion FROM caso WHERE id = 10;
SELECT evento, estado_anterior, estado_nuevo, usuario_id, fecha
FROM historial WHERE caso_id = 10 ORDER BY id;
```

5. Reiniciar la aplicación y comprobar que estado, historial y fecha se conservan.
6. Para rechazos de permisos y saltos, usar la API directamente; por ejemplo:

```powershell
$body = @{ estado = 'En análisis'; usuario_id = 1 } | ConvertTo-Json
Invoke-RestMethod -Method Patch -Uri 'http://localhost:3000/api/casos/10/estado' `
  -ContentType 'application/json' -Body $body
```

El Solicitante recibe 403. Un salto desde Pendiente a En atención recibe 409.
No deben cambiar el estado ni agregar eventos. Sustituir `10` por el caso de prueba.

## Integración en HU-03

La bandeja de Keyla se integró mediante PR #25. La integración del 9 de octubre
añade la columna Acciones y carga `estado-caso.css` y `estado-caso.js` antes de
`bandeja.js`. Cada fila usa `CampusHelpEstados.crearControlEstado()` y obtiene
el agente de `inicializarActuarComo()`; al cambiar de usuario se actualizan los
controles y se recarga la tabla conservando el orden del servidor.

Tras guardar se confirma el estado y se consulta otra vez la bandeja. Si falla
esa consulta, se conserva la tabla, el estado actualizado y el botón del
siguiente estado; se informa que el cambio se guardó pero no se pudo refrescar.
Los rechazos de la API mantienen el estado y muestran el error en la fila.

`casosRepository.listar()` ahora incluye `agente_id`, además del nombre `agente`,
para enlazar `atender.html?id=<caso>` solo en los casos En atención asignados al
agente seleccionado. `atender.html` añade el regreso a la bandeja. La asignación
y la restricción del cambio de estado al agente asignado permanecen en HU-04;
esta entrega valida la regla original de HU-05, que permite cualquier agente activo.

## Evidencia del 9 de octubre de 2026

Validación completa con **MySQL 8.0.46 y Chrome**, usando bases temporales:
**119 pruebas aprobadas, 0 fallidas, 0 omitidas**. Incluye las regresiones de
HU-01/HU-02/HU-03/HU-06, las suites MySQL de HU-05/HU-06 y ocho pruebas de
navegador (la suite y sus siete escenarios) en `tests/browser/bandeja.mysql.test.js`.

Se verificó el flujo desde la bandeja hasta En validación, historial y autor,
fecha de primera atención, doble clic con un solo cambio, cambio de agente,
error sin solución, formulario de atención y regreso a la bandeja, recarga
fallida después de guardar y continuación, persistencia al recargar, lista vacía,
ausencia de agentes, campos escapados y CP-04/CP-05/CP-14/CP-15. Las suites MySQL conservan los escenarios
de rollback real, concurrencia y persistencia tras reiniciar servidor y conexiones.

La prueba prepara un caso asignado únicamente en su BD temporal, porque HU-04
todavía no implementa la asignación. No ejecuta `db:init` ni modifica `campushelp`.
Las tres bases temporales se eliminan al terminar, así como el perfil de Chrome.

Para reproducir la suite completa (navegador: Node.js 22+, Chrome o Edge):

```powershell
$env:CAMPUSHELP_TEST_MYSQL = '1'
$env:CAMPUSHELP_TEST_BROWSER = '1'
try { npm.cmd test } finally {
  Remove-Item Env:CAMPUSHELP_TEST_MYSQL
  Remove-Item Env:CAMPUSHELP_TEST_BROWSER
}
```

La prueba detecta Chrome o Edge en Windows. En otra instalación, indicar la
ruta del ejecutable en `CAMPUSHELP_BROWSER`. `npm test` sin variables no requiere
MySQL ni navegador y omite esas tres suites. La aplicación sigue admitiendo Node.js 18+.
