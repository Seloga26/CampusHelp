# HU-05 — Guía de implementación, pruebas e integración

Issue: [#5](https://github.com/Seloga26/CampusHelp/issues/5). Responsable: Miguel
(@miguelfsociety). Rama local: `feature/HU-05-cambiar-estado`.

## Implementación

- `src/services/casos/cambiarEstado.js`: validación de IDs, agente y transición;
  coordina caso + historial mediante `enTransaccion`. Errores de dominio 400,
  403, 404 y 409. Recibe las dependencias del contenedor.
- `src/repositories/casosRepository.js`: búsqueda con `SELECT … FOR UPDATE` para
  validar cambios concurrentes; actualización y fecha inicial con `COALESCE`;
  consulta final con área, categoría, solicitante y agente.
- `src/repositories/historialRepository.js`: repositorio de HU-01 reutilizado para
  registrar el evento con la misma conexión de la transacción.
- `src/routes/casosRoutes.js`: la ruta PATCH de HU-05 ya está conectada al servicio
  desde la refactorización de ADR-003 y se conserva.
- `public/js/estado-caso.js`: control para el siguiente estado, errores visibles,
  actualización tras guardar y protección frente a doble clic.
- `/cambiar-estado.html`: pantalla independiente con selector de agentes para
  trabajar mientras se integra HU-03. No consulta ni implementa la bandeja.

El cierre y la devolución desde validación siguen reservados a HU-07. En Sprint 1
se permite actuar a cualquier agente activo, según el refinamiento de la historia.

## Prueba automática con MySQL real

Con MySQL 8 disponible y las credenciales de `.env` configuradas:

```powershell
$env:CAMPUSHELP_TEST_MYSQL = '1'
node --test tests/casosEstado.mysql.test.js
Remove-Item Env:CAMPUSHELP_TEST_MYSQL
```

La cuenta necesita permisos para crear una base temporal y triggers. La prueba
crea `campushelp_hu05_test_<identificador aleatorio>`, aplica esquema y seed en esa
base y la elimina al terminar. La base de la aplicación no se altera. Incluye los
criterios de aceptación, fechas, dos cambios simultáneos y un fallo deliberado de
INSERT en historial para verificar rollback real. Se omite en `npm test` normal.

## Prueba manual de la pantalla

1. Iniciar MySQL y `npm start`. La base debe tener al menos un caso; el seed base
   aún no contiene casos (T0 corresponde a HU-03). Usar un caso existente del
   equipo o registrar uno desde `/registrar.html` (HU-01 ya está integrada).
2. Abrir `http://localhost:3000/cambiar-estado.html`, seleccionar Carla o Diego,
   indicar el ID y su estado actual y pulsar **Preparar cambio**.
3. Pulsar **Pasar a En análisis**, luego **Pasar a En atención**, y finalmente
   **Pasar a En validación**. El estado mostrado debe actualizarse tras cada éxito.
4. Consultar la BD con el ID utilizado:

```sql
SELECT id, estado, fecha_inicio_atencion FROM caso WHERE id = 10;
SELECT evento, estado_anterior, estado_nuevo, usuario_id, fecha
FROM historial WHERE caso_id = 10 ORDER BY id;
```

5. Reiniciar la aplicación y comprobar que estado, historial y fecha se conservan.
6. Para rechazos de permisos y saltos, usar la API directamente; por ejemplo:

```powershell
$body = @{ estado = 'En análisis'; usuario_id = 1 } | ConvertTo-Json
Invoke-RestMethod -Method Patch -Uri 'http://localhost:3000/api/casos/10/estado' `
  -ContentType 'application/json' -Body $body
```

El Solicitante recibe 403. Un salto desde Pendiente a En atención recibe 409.
No deben cambiar el estado ni agregar eventos. Sustituir `10` por el caso de prueba.

## Integración en HU-03

La bandeja no está publicada en ninguna rama remota al revisar el repositorio.
Cuando exista, añadir a `bandeja.html`, antes de `js/bandeja.js`:

```html
<link rel="stylesheet" href="css/estado-caso.css">
<script src="js/estado-caso.js"></script>
```

Al renderizar cada caso, agregar el control a la celda de acciones:

```js
const control = CampusHelpEstados.crearControlEstado({
  caso,
  obtenerUsuario: () => usuarioSeleccionado, // { id, rol } del selector común
  alActualizar: () => cargarBandeja(),
});
celdaAcciones.append(control.elemento);
// Al cambiar "Actuar como", llamar control.actualizarUsuario() para cada fila.
```

`usuarioSeleccionado`, `cargarBandeja()` y `celdaAcciones` representan las variables
que HU-03 defina. HU-01 ya publicó `comun.js`: `inicializarActuarComo()` entrega el
usuario elegido en su callback `onChange`, y `api()` llama a la API. El control
mezcla la respuesta actualizada con el caso original para conservar área/categoría
y otros campos de la consulta. Un fallo al refrescar después de guardar muestra
que el cambio ya se guardó y permite recargar la página.
